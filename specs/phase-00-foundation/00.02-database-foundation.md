# Task 00.02 — Database Foundation

**Date:** 2026-08-12  
**Status:** Proposed for written-spec review  
**Depends on:** Task 00.01 and repository checkpoint `10ffb84`

## Goal

Create a production-oriented PostgreSQL/PostGIS migration and transaction
foundation for İkiMetr without defining any business entities.

PostgreSQL remains the source of truth. This task establishes how schema changes
are versioned, reviewed, applied, verified, and recovered before authentication,
authorization, realtor, property, request, ingestion, or matching tables exist.

## Selected approach

Use `node-pg-migrate@9.0.0`, pinned exactly in the lockfile, as the
PostgreSQL-specific migration engine.

Reasons:

- it targets PostgreSQL directly;
- it supports ordered up/down migrations and transactional execution;
- it uses the existing `pg` driver;
- version 9.0.0 supports Node.js 22+ and PostgreSQL 14+, matching İkiMetr's
  Node.js 24 and PostgreSQL 17 baseline;
- it does not force an ORM or prematurely define future business models.

Do not introduce Drizzle, Prisma, TypeORM, Sequelize, Knex, another migration
engine, or a custom migration runner in this task.

Because immutable-content checking is not a guaranteed built-in v9 contract,
İkiMetr adds a small deterministic SHA-256 manifest verifier around migration
files. This verifier checks repository integrity only; it does not execute SQL
or replace `node-pg-migrate`.

## Scope

### In scope

1. Add the pinned migration dependency and explicit package scripts.
2. Add an ordered migration directory and one initial foundation migration.
3. Enable required PostgreSQL extensions.
4. Create empty technical schemas.
5. Establish portable least-privilege ownership/grant contracts.
6. Add a migration checksum manifest and deterministic verifier.
7. Add an explicit transaction helper to `@ikimetr/database`.
8. Test clean apply, repeat apply, transaction rollback, extension/schema
   presence, checksum failure, and concurrent migration safety.
9. Document local commands and production migration rules.

### Out of scope

- Authentication, sessions, users, roles as business entities, realtor
  profiles, clients, properties, listings, requests, matches, owner records,
  contact data, ingestion records, queues, audit events, notifications, or
  moderation tables.
- Row-level security policies for nonexistent business tables.
- Supabase-specific schemas or managed-service coupling.
- ORM selection or typed domain repositories.
- Seeds, fixtures containing business data, example users, or production data.
- Automatic migration during API, web, or worker startup.
- Destructive production rollback automation.
- Redis, object storage, search, AI, scraping, or UI changes.
- Database backup/restore implementation; that is a separate operational task.
- Changing the Project Constitution or core domain model.

## Database baseline

- PostgreSQL: 17.
- PostGIS image: `postgis/postgis:17-3.5`.
- Connection source: `DATABASE_URL` only.
- Connection URLs, usernames, passwords, and raw environment values must never
  be logged.
- Development binds PostgreSQL only to `127.0.0.1`.
- Application startup must not run migrations.

## Initial migration

The first migration creates only foundation objects.

### Extensions

Create with `IF NOT EXISTS`:

- `postgis` — future geospatial property/location queries;
- `pgcrypto` — future database-side cryptographic primitives and UUID support
  where explicitly approved;
- `citext` — future case-insensitive identifiers where a domain design
  requires them.

Installing an extension does not authorize business code to use it without its
own task specification.

### Schemas

Create with `IF NOT EXISTS`:

- `app` — future core business data;
- `audit` — future append-only security/audit records;
- `ingestion` — future untrusted external-data pipeline.

The schemas remain empty in Task 00.02.

### Privilege baseline

- Revoke `CREATE` on schema `public` from `PUBLIC`.
- Do not revoke `USAGE` on `public` because installed extensions may expose
  objects there.
- No anonymous/public grants are added to `app`, `audit`, or `ingestion`.
- Do not create LOGIN roles or commit credentials.
- Define three NOLOGIN group roles for the local/self-hosted PostgreSQL
  baseline:
  - `ikimetr_app`;
  - `ikimetr_worker`;
  - `ikimetr_migrator`.
- Role creation must be idempotent and must not assign passwords.
- `ikimetr_migrator` owns migration-created schemas/objects.
- `ikimetr_app` and `ikimetr_worker` receive no table privileges because no
  tables exist yet.
- Future tasks grant only object-specific privileges and define default
  privileges explicitly.
- If a managed PostgreSQL provider does not permit role creation or ownership
  changes, deployment must use a provider-specific provisioning step reviewed
  separately; migrations must not silently broaden privileges as a fallback.

### Migration history

Use a dedicated migration-history schema/table configured through
`node-pg-migrate`:

- schema: `migration`;
- table: `pgmigrations`.

The history contains migration identity and execution metadata required by the
tool. It must not contain credentials, SQL inputs, PII, or application data.

## Migration integrity

Store a committed manifest beside the migrations. For every migration it
records:

- repository-relative normalized path;
- SHA-256 of the exact UTF-8 file bytes.

The verifier must:

1. reject a missing manifest entry;
2. reject a manifest entry without a file;
3. reject a hash mismatch;
4. reject duplicate normalized paths;
5. reject paths outside the migration directory;
6. produce stable output ordering;
7. never read `.env`, connect to PostgreSQL, or print file contents;
8. return nonzero on any violation.

Creating a new migration requires updating the manifest in the same change.
Editing an already merged/applied migration is prohibited. Corrections use a new
forward migration.

## Migration execution contract

Provide explicit scripts from the repository root:

- `db:migrate:verify` — checksum/manifest verification only;
- `db:migrate:up` — verify, then apply pending migrations;
- `db:migrate:down:local` — local/test rollback of exactly one migration;
- `db:migrate:create` — create a new ordered migration template.

Rules:

- `up` runs only as an explicit deployment/developer command.
- Each migration is transactional unless its file explicitly declares a
  reviewed non-transactional exception.
- Concurrent migration processes must serialize through the migration engine's
  PostgreSQL advisory-lock behavior.
- A failed transactional migration leaves neither partial schema objects nor a
  successful history row.
- Re-running `up` with no pending migration is a no-op.
- Production rollback is forward-only: create a corrective migration.
- `db:migrate:down:local` must refuse to run when
  `NODE_ENV=production`.
- No script may echo `DATABASE_URL`.

## Database package API

Keep `createDatabaseConnection(connectionString)` backward compatible.

Add a focused transaction boundary:

```ts
export interface DatabaseTransaction {
  query<T extends QueryResultRow = QueryResultRow>(
    text: string,
    values?: readonly unknown[],
  ): Promise<QueryResult<T>>;
}

export interface DatabaseConnection {
  check(): Promise<void>;
  transaction<T>(
    work: (transaction: DatabaseTransaction) => Promise<T>,
  ): Promise<T>;
  close(): Promise<void>;
}
```

Behavior:

1. Acquire one pool client.
2. Execute `BEGIN`.
3. Call the callback with a query-only transaction capability.
4. On success execute `COMMIT` and return the callback result.
5. On callback or commit failure attempt `ROLLBACK`.
6. Always release the client exactly once.
7. Preserve the original failure; a rollback failure must not replace it.
8. Never retry automatically.
9. Never expose the raw pool/client through the public API.
10. After `close()`, `check()` and `transaction()` fail predictably without
    creating a new pool.

No domain repository or arbitrary migration execution API is added.

## Error handling and observability

- Migration and transaction errors may include operation and migration names,
  but never connection strings, passwords, SQL parameter values, or full
  sensitive SQL payloads.
- The migration command exits nonzero on verification, connection, lock, or SQL
  failure.
- Application health remains `SELECT 1`; it must not mutate state.
- No automatic retry is added.
- No migration telemetry is sent externally.

## Testing strategy

### Unit tests

Prove:

1. transaction success commits once and returns the callback value;
2. callback failure rolls back once;
3. commit failure attempts rollback;
4. rollback failure preserves the original error;
5. client release occurs exactly once on every path;
6. no retry occurs;
7. closed connection rejects future work;
8. manifest verification accepts the committed set;
9. missing, extra, duplicate, escaping, and hash-mismatched entries fail without
   exposing file contents.

Database doubles are allowed only for transaction state-machine unit tests.

### Integration tests

Using the existing localhost Docker PostgreSQL:

1. apply all migrations to a clean isolated test database;
2. verify `postgis`, `pgcrypto`, and `citext` are installed;
3. verify `app`, `audit`, `ingestion`, and `migration` schemas exist;
4. verify no business tables exist;
5. verify the three group roles are NOLOGIN;
6. verify `PUBLIC` cannot create objects in schema `public`;
7. run `up` again and confirm a no-op;
8. introduce a temporary failing transactional migration and prove its objects
   and history row are absent afterward;
9. start two migration attempts and prove no duplicate/partial application;
10. prove one local down/up cycle on an isolated disposable database;
11. keep the existing connectivity health test passing.

Tests must not drop, reset, or reuse a non-test database. The test database name
must be derived from a fixed safe prefix plus a random suffix, validated before
creation or deletion, and cleaned in `finally`.

## Security constraints

- No secrets or real credentials in Git.
- No business or personal data.
- No raw client/user identifiers.
- No dynamic SQL identifiers from untrusted input.
- No `CASCADE` database/schema drop outside validated disposable test
  databases.
- No superuser connection in application runtime.
- Migration credentials are deployment-only and separate from future app/worker
  credentials.
- Workers do not receive migration privileges.
- SQL and model output are never executed automatically.
- Any destructive migration requires a separate specification, backup/restore
  evidence, and explicit approval.

## Definition of Done

- `node-pg-migrate@9.0.0` is pinned.
- Migration manifest verification passes.
- A clean isolated database migrates from zero to current.
- Repeated `up` is a no-op.
- Transaction failure leaves no partial objects or history.
- Concurrent migration execution is safe.
- Required extensions and empty schemas exist.
- No business tables exist.
- NOLOGIN group roles and baseline grants match this specification.
- Transaction API unit and integration tests pass.
- Local-only down guard passes.
- Scope check and secret scan pass.
- `pnpm format:check`, `pnpm lint`, `pnpm typecheck`,
  `pnpm test:unit`, `pnpm test:integration`, `pnpm build`, and
  `pnpm audit:prod` pass.
- README documents exact migration workflow and production constraints.
- The final handoff records migration version, commands, results, limitations,
  and the next task without starting it.

## Stop conditions

Stop and request a separate decision if implementation evidence shows that:

- `node-pg-migrate@9.0.0` cannot run reliably under the pinned Node/PostgreSQL
  versions;
- advisory locking is absent or cannot be verified;
- role creation requires unsafe privilege broadening;
- extensions cannot be installed transactionally in the target environment;
- an application/domain file must change;
- a business table or API contract appears necessary;
- a destructive action would target a non-disposable database.
